# RWI Controlled Live Pilot 5F — Preserve Source-Provided Airport Identity Evidence

Status: IMPLEMENTED, ADVERSARIALLY REVIEWED, COMMITTED. §10 below documents the review's own independent findings: two genuine 5F extraction defects (fixed before commit) and a separate, pre-existing, out-of-scope UAC3/guard architecture question the review answers but does not fix.

## 1. Problem

Controlled Live Pilot 5E reached LEVEL 5 (governed preview) on a real MAC document whose agenda title explicitly reads *"2026 Anoka County-Blaine Airport Runway 18-36 Pavement Reconstruction and Electrical Vault Improvements"* — but the resulting `CandidateFragment` carried `airport_names = frozenset()`. With no name evidence, the guard evaluated five real, topology-matched candidate airports (none of them Anoka, none of them MSP) and correctly returned `REVIEW_REQUIRED` — an honest but avoidable ambiguity, since the source itself already states which airport the item concerns.

## 2. Data-flow trace (re-derived from current code, not the 5E report)

`MACGranicusAgendaItemCandidate.item_title` (the agenda title) → passed as `document_title=item.item_title` into `extract_candidate_fragment()` (`scripts/capture_mac_discovery.py`) → forwarded unchanged into `_fragment_from_text()` (`app/acquisition/mac_granicus_extractor.py`) → stored on `CandidateFragment.document_title` → forwarded unchanged into `EvidenceBag.document_title` (`candidate_fragment_to_evidence_bag()`) → per the guard's own module docstring, `document_title` is "carried through into the decision's reason text only - never used in the decision algorithm itself."

`CandidateFragment`'s own class docstring independently confirms this is by design: it explicitly buckets `document_title` (along with `url`, `publication_date`, `parser_identifier`, `extracted_at`, `discovery_context`) as **AUDIT_ONLY**, distinct from the **OPTIONAL EXTRACTED VALUES: mapped to EvidenceBag** bucket that `airport_names` belongs to.

Separately confirmed: `_fragment_from_text()`'s `CandidateFragment(...)` constructor call never passed `airport_names=` at all before this fix — a repo-wide `grep` for `airport_names=` across `app/acquisition/` returned zero matches. This extractor has never had any airport-name-extraction capability, from any source, for any document.

## 4. Architectural verdict: D (MULTIPLE) — A and C both apply, with an important qualifier

**A applies**: source-provided title evidence exists and was never preserved into the evidence contract.

**C also applies, but is deliberately NOT fixed in this mission**: the PDF body independently contains even stronger identity evidence (the airport name in direct apposition with its FAA-LID code, `"Anoka County-Blaine Airport (ANE)"`). However, direct inspection of the same real document found it **also** mentions two *other* airports for unrelated reasons: *"...to reduce congestion at the Minneapolis-St. Paul International Airport..."* (background/purpose context) and *"...funds from the 2026 Flying Cloud Airport (FCM) ... project be reallocated..."* (an unrelated funding cross-reference). A naive body-text scan using the same structural rule this mission implements was tested directly against the real document and confirmed to extract all three names plus a newline-corrupted PDF-extraction artifact — exactly the contamination the guard's contradiction machinery exists to arbitrate, not something a regex can safely pre-judge without much more sophisticated (and not yet justified) sentence-structure awareness. Body-text extraction is explicitly deferred as a separate, future, more carefully-designed mission — not attempted here.

## 5. Implementation

One new structural rule in `app/acquisition/mac_granicus_extractor.py`, matched **only against `document_title`**, never the PDF body:

- `_AIRPORT_NAME_IN_TITLE`: 1–5 capitalized tokens (allowing internal periods/apostrophes/hyphens, e.g. `"St."`, `"County-Blaine"`) immediately followed by the singular word `"Airport"`. The trailing `\b` after `"Airport"` already excludes the plural `"Airports"` (no word boundary between `t` and a directly-following `s`) — this is what keeps `"Metropolitan Airports Commission"` from ever matching, with no special case needed. A negative lookahead rejects `"Airport"` immediately followed by a common street-suffix word (`Road`, `Boulevard`, `Drive`, etc.), defending against real street-naming patterns like `"Airport Road"`.
- `_extract_airport_names_from_title()`: applies the regex, returns a `frozenset`. No dedup/single-pick logic — if a title ever named more than one airport, all would be preserved and the existing, unmodified UAC3 seed-formability rule (`_extract_unknown_airport_candidate_seed()`, unchanged) would correctly treat that as not-formable, exactly as it already does for any multi-name fragment.
- Wired into `_fragment_from_text()`: `airport_names = _extract_airport_names_from_title(document_title)`, passed into the existing `CandidateFragment(...)` constructor call.

No other file touched. `mac_granicus.py` (acquisition/discovery layer) does not construct `CandidateFragment` and needed no change. `discovery_candidate_fragment.py`, `evidence_attachment_guard.py`, `discovery_evidence_persistence.py`, `unknown_airport_discovery_integration.py`, `capture_mac_discovery.py` — all untouched, confirmed by `git status`. No schema/migration change. No hardcoded airport name, runway number, or FAA/IATA/ICAO code anywhere in the new logic.

## 7. Replay/idempotency impact (question 10, flagged HIGH PRIORITY by the review mission)

If a fragment with this exact identity were captured under the *old* extractor (empty `airport_names`) and later replayed under this *new* extractor (populated `airport_names`), the resulting `EvidenceBag` serialization would differ, and EB3's `_reconcile_replay_snapshot()` (`app/services/discovery_evidence_persistence.py`, unmodified) would correctly raise `ConflictingEvidenceBagReplayError` rather than silently accepting drifted content — this exact mechanism (including the harder case where a second row is already flushed before the conflict surfaces) was already proven, through the real runner, by `test_evidence_bag_replay_conflict_fails_loud_through_runner_not_swallowed` (added during the UAC7 adversarial review). No new production code was needed to preserve this protection; it was not weakened. In practice, this specific document has never been applied to the real database (5D/5E/5F were all preview-only), so no actual replay-conflict is reachable for it today — but the general protection remains intact for any future case.

## 8. Contradiction preservation (mission §10)

Given the title-only design decision (§4), there is no code path under this fix where a title-derived name and a body-derived name could simultaneously become competing `airport_names` claims for the guard to arbitrate — the body is never mined for names at all in this mission. No contradiction-preservation test is reachable under the current, deliberately narrower contract this fix implements; this is reported honestly rather than fabricated. Should a future mission extend extraction to the PDF body, that is precisely where `contradicting_names` (already a first-class `CandidateFragment`/`EvidenceBag` field, already fully supported by the guard, untouched here) would become the correct mechanism — not something to invent now.

## 10. Adversarial review findings

An independent adversarial review re-derived every claim above from source and empirical testing rather than trusting this report. Two genuine defects were found in the 5F extraction logic itself and fixed before commit; one separate, real, pre-existing architecture question was investigated and answered, but deliberately not fixed (out of this mission's scope).

### 10.1 Title-to-document linkage is a proximity heuristic, not a guaranteed structural pairing (pre-existing, NOT a 5F defect, NOT fixed here)

`discover_agenda_items()` (`app/acquisition/mac_granicus.py`, unmodified by 5F) finds every agenda item-number+title block via `_AGENDA_ITEM.finditer()`, then for each one searches an **800-character window immediately following that match** for the nearest `MetaViewer.php` document link (`_META_LINK.search(window)`). This is a nearest-following-link heuristic, not a guaranteed same-row or same-block pairing. If a real agenda item has no document link of its own but a *later* item's link falls within its 800-character window, `discover_agenda_items()` would silently pair the first item's title with the second item's document — there is no positive verification that a found link actually belongs to the title it gets attached to.

In every real agenda page structure observed across Pilots 5B–5E (dozens of real items, confirmed via the committed `AGENDA_HTML` test fixture's own shape), each item's own document link consistently appears immediately after its own title, before the next item's row begins — so this risk has not been observed to manifest in practice. But the code contains no explicit safeguard against it, and 5F's own new capability (mining `document_title` for identity evidence) makes a hypothetical mismatch **more consequential than before**: previously a title/document mismatch could only produce a wrong *relevance* judgment; now it could also inject a wrong *airport-name claim* into the evidence for an unrelated document.

This is squarely a pre-existing characteristic of `mac_granicus.py`, entirely untouched by the 5F diff. Per this review's own correction policy, it is **not modified here** — reported as a separate, real finding for a future, explicitly-scoped hardening mission (e.g., verifying the found link's own anchor text or position falls within the *same* table row as its title, not merely within a fixed character window).

### 10.2 Two genuine 5F extraction defects found and fixed

**Defect 1 — connector-word truncation.** `_AIRPORT_NAME_IN_TITLE`'s original pattern (`(?:[A-Z][\w.'-]*\s+){1,5}Airport`) required every token in the name to be capitalized, with no tolerance for lowercase connector words. Attacking the mission's own named example, **"Bill and Hillary Clinton National Airport"** (the real name of one of the five candidate airports evaluated in the actual 5E/5F scenario), the lowercase "and" broke the match chain and the regex silently restarted at "Hillary," extracting the truncated, wrong string `"Hillary Clinton National Airport"`. Fixed by allowing the literal connector `and` as an interior token, gated by a negative lookahead so `and` is never accepted immediately before `Airport` itself (`and(?!\s+Airport\b)`) — this is what keeps a genuinely different case ("Roads and Airport Improvements") from becoming a false positive.

**Defect 2 — two-airport merge.** Testing a title naming two distinct real airports joined by "and" (`"Example Regional Airport and Sample Municipal Airport..."`) found the fix for Defect 1 introduced a new problem: because the word `"Airport"` itself starts with a capital letter, it satisfied the generic capitalized-token alternative inside the optional repetition group, so the regex greedily matched through the *first* `"Airport"` as if it were filler, producing one bogus merged name (`"Example Regional Airport and Sample Municipal Airport"`) instead of two independent claims. Fixed by excluding the literal word `Airport` from the generic-filler alternative (`(?!Airport\b)[A-Z][\w.'-]*`), so it always terminates a match rather than being swallowed into a longer one.

Both defects were found by directly attacking the mission's own named examples (§5, §7) against the real production function — not invented speculatively — and both are now covered by dedicated regression tests, including the exact real candidate-airport name from the actual 5E scenario.

### 10.3 UAC3/guard precedence — empirically re-derived, `UAC3_PRECEDENCE_REQUIRES_SEPARATE_REVIEW`

UAC3's locked design rationale (`unknown_airport_discovery_integration.py`'s own module comment): *"ambiguity among KNOWN candidates is an ordinary human identity-review case, never a reason to fabricate a 'new airport' candidate merely because matching was ambiguous - the true airport is presumably ALREADY one of the plausible known candidates."*

Three scenarios were run directly against the real, unmodified `evaluate_attachment_for_candidates()` (not reasoned about abstractly):

- **Scenario A** (mission's own naming) — explicit unknown name + topology matching 2 known candidates: both candidates land on `REVIEW_REQUIRED`. This is the exact real Anoka case. The design's own foundational assumption — "the true airport is presumably already one of the plausible known candidates" — is empirically false here: the true airport (Anoka County-Blaine) is explicitly named and matches neither candidate.
- **Scenario B** — explicit name *exactly* matching one candidate (2 independent categories: name + topology) while topology alone matches a second, unrelated candidate: **both are downgraded to `REVIEW_REQUIRED`**, including the candidate with the genuine 2-category match. `evaluate_attachment_for_candidates()`'s own cross-candidate check treats any candidate reaching `ATTACH_CONFIRMED` *or* `ATTACH_PROVISIONAL` as "qualifying" and downgrades all qualifying candidates together whenever more than one qualifies — it does not distinguish a strong (multi-category) match from a weak (single-category) one when deciding whether ambiguity exists.
- **A third, more serious case, found while testing B** — a *single*, non-ambiguous topology match (only one candidate shares the topology, so no cross-candidate downgrade triggers) **combined with an explicit, unmatched, contradicting name claim** yields `ATTACH_PROVISIONAL` for that one candidate — which is a `KNOWN_MATCH` bucket outcome. UAC3 would route this to `KNOWN_CANONICAL_ATTACHMENT`, silently setting `attached_airport_id` to the wrong airport, **without ever reaching human review at all** — worse than the ambiguous case, which at least stops for a human. This happens because the guard's name-evidence handling is deliberately positive-only (an unmatched name is never automatically treated as a contradiction, per its own documented design — "never guesses that a found name belongs to some other, unspecified airport").
- **Sanity check (zero topology overlap)**: correctly falls to `INSUFFICIENT_IDENTITY`, matching Controlled Rehearsal #1's own already-proven unknown-candidate path.

**Verdict: `UAC3_PRECEDENCE_REQUIRES_SEPARATE_REVIEW`**, not `UAC3_PRECEDENCE_CORRECT`. The current precedence is a defensible, conservative default, but its own stated justification does not hold in at least three concretely reachable, evidence-backed scenarios — one of which (the single-match case) can silently attach evidence to the wrong airport without any human review, which is a materially different (and more concerning) risk than "merely" failing to discover a new airport. **Neither `evidence_attachment_guard.py` nor `unknown_airport_discovery_integration.py` was modified in this mission** — both remain exactly as committed. This is reported as a separate architectural finding for a future, explicitly-scoped review, per this mission's own instruction not to conflate it with 5F's own commit decision.

### 10.4 Unknown-airport strategic answer (mission §14): DEPENDS, leaning NO for the realistic case

Can RWI currently form an `UnknownAirportCandidate` for a real, previously-unknown airport that is explicitly named by the source, when its runway topology happens to overlap known airports? **Only when that topology overlaps *zero* known airports.** The moment it overlaps even *one* known airport (§10.3's third case) or *more than one* (§10.3 Scenario A), the explicit name evidence is structurally unable to override the topology-based routing decision — regardless of how confidently and unambiguously the source names the true airport. Given real-world runway headings are drawn from a small, geography-driven set of common values shared by many airports worldwide, "zero overlap" is the exception rather than the rule for a plausible newly-discovered airport, not a rare edge case. This is directly material to RWI's stated worldwide-EMAS-discovery goal, exactly as the review mission anticipated — reported here, not fixed.
